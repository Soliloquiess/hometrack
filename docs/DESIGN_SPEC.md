🔴 **단위가 두 종류다. 섞으면 1만배 오차가 난다.**

| 대상 | 단위 | 함수 | 출력 예 |
|---|---|---|---|
| 공고 보증금 · 예산 · 자산 | **만원** | `won()` | `2억 1,000만원` |
| 월임대료 · 월세 상한 | **만원** | 직접 | `18만원` |
| 소득 기준액 (`income_tables`) | **원(월)** | `krwMonth()` | `5,760,000원` |
| 연소득 입력 | **만원** | `won()` | `6,000만원` |

연소득을 월평균으로 바꿀 때만 `연소득 × 10000 ÷ 12` 로 원 단위에 맞춘다.
**이 변환은 소득 판정 한 곳에만 둔다.** 여러 곳에 흩어지면 어디서 1만배가 어긋났는지 찾을 수 없다.

**금액 표기 함수를 우회하지 않는다** — `wonRange(a, b)` 는 **양쪽 모두** `won()` 을 지난다(M4).
v1.1 은 하한만 `toLocaleString()` 으로 찍어 `15,000 ~ 2억 4,000만원` 이 화면에 그대로 나왔다.
`null` 이 섞인 숫자는 `num()`(건수·월세) / `krwMonth()`(원 단위) 를 지나 `—` 가 되게 한다 — `3,000 / null` 이 나오면 안 된다(M19).

🔴 **날짜 산술은 두 가지 함정이 있다** (M12·M13).

| 함정 | 잘못된 방식 | v1.2 규칙 |
|---|---|---|
| 개월 차 | 월 번호만 빼기(`12-31` → `03-01` = 3개월) | **일수 기준 환산** — `daysBetween / 30.4375`. 월 번호만 빼면 `pre_marriage_within_months: 3` 이 최대 1개월 관대해진다 |
| 날짜 파싱 | `new Date("2026-09-03")` 은 **UTC 자정**, `new Date("2026-09-03 07:02")` 은 **로컬** | `parseDT()` 가 날짜만이면 **`T00:00:00` 을 붙여** 로컬로 고정한다. 섞으면 KST 에서 `future(today) === true` 가 되고 음수 오프셋 브라우저에서 D-day 가 하루 밀린다 |

`parseDT()` 는 파싱 실패 시 `Invalid Date` 가 아니라 **`null`** 을 돌려준다 — 호출부가 `isNaN` 을 매번 챙기지 않게 하기 위해서다.

**소득 기준액은 가구원수 × 비율 2차원 표에서 직접 읽는다** (SPEC §3-6).

```
적용비율 = (맞벌이면 pct_dual, 아니면 pct) + pct_adjust_by_household[가구원수]     ← D2
기준액   = income_tables[basis].by_household[가구원수][적용비율]                     ← 합산 비율이 조회 키
```

🔴 **가산이 빠지면 이 도구의 기본 사용자(2인)에게 잘못된 "불가"가 난다** (D2 · 검수 P2).
공식 원문은 "계층별 소득기준에 **1인 가구 20%p, 2인 가구 10%p 각각 가산**"이다.
행복주택 2인 예비신혼부부는 100%가 아니라 **110%**(맞벌이 120% → **130%**)를 본다.
해당 정책들은 `confidence: official` 이라 강등 게이트 3종 어디에도 걸리지 않는다 —
즉 **가산 누락은 원칙 9로도 막히지 않고 그대로 "불가"로 나간다.**

| 항목 | 값 | 출처 |
|---|---|---|
| 가산표 | `policies[].criteria.income.pct_adjust_by_household` (예: `{"1":20,"2":10}`) | `policies.json` |
| 키가 없는 가구원수 | 가산 **0** (3인 이상은 100%/120% 그대로) | D2 |
| `pct_dual` 이 `null` | 맞벌이여도 `pct` 를 쓴다 (국민임대·통합공공임대) | SPEC §3-2 |

**표기 규칙** — 적용비율은 **합산값 + 내역**을 함께 적는다. 합산값만 적으면 사용자가 원문 비율과 대조할 수 없고,
기본 비율만 적으면 자기 기준액과 대조할 수 없다.

```
2인 · 130%(120%+10%p 가산) 적용액 7,626,151원   2026년도 적용기준(2025년 실적)
                                                  ↑ .yl year_label
```
가산이 0 이면 괄호를 붙이지 않는다(`3인 · 120% 적용액 …`).

| 표 조회 결과 | 화면 |
|---|---|
| 합산 비율 칸이 있음 | 그 값을 그대로 쓴다. 표시 없음 |
| 합산 비율 칸은 없고 `100%` 는 있음 | `100% × 적용비율 ÷ 100` 폴백 + **`근사값` 칩** |
| `100%` 도 없거나 가구원수 행이 없음 | 판정하지 않고 `조건부 — 기준액 미확보` |

🔴 **비율을 100% 값에 곱해서 만들어 놓고 근사값 표시를 빼면 안 된다.**
공표표는 비율별로 반올림이 들어갈 수 있어 곱셈 결과와 어긋난다. 어긋난 값을 정확한 값처럼 보여주는 것이 가장 나쁘다.
`year_label`(예: `2026년도 적용기준(2025년 실적)`)을 **적용액 옆에 항상 함께** 찍는다.
적용년도와 실적년도가 1년 차이라 사용자가 "올해 값인가"를 반드시 묻게 된다.

**실측**(연구자 확정 표 기준): 도시근로자 2인 `110` = 6,452,897원 · `130` = 7,626,151원 (직접 조회, 근사값 아님).
기준중위소득 2인은 `110` 칸이 없어 통합공공임대(100%+10%p)가 **`근사값`** 경로로 간다 — 고시가 100%만 공표하기 때문이다.

  화면이 사실과 다른 말을 하고, SPEC §2 표가 정한 정상 표시(`정리 YYYY-MM-DD`)가 소리 없이 사라진다.

  🔴 **`hold` 의 정본은 `diff.collector_failures[].status` 다.** 수집기 자체는 성공했으므로
  `collectors[].status` 는 `"ok"` 로 남는다 — 화면은 `holdOf(key)` 로 diff 를 조회해 그 줄만 `--mid` 로 바꾼다.
  `collectors[].status` 가 직접 `"hold"` 로 오는 경우도 함께 받는다(수집기가 승격 보고할 때).
  판정 우선순위는 `fail` > `hold` — 수집기가 실패한 회차에는 실패를 먼저 알린다.
- **실패 줄에는 직전 성공 시각 + 실패 사유가 반드시 함께** 들어간다.
- 수동 줄에는 **원문 목록 링크**를 붙인다. 사람이 등록하러 갈 곳이 화면에 있어야 한다.
- 🔴 **LH 줄은 두 줄로 나눠 적는다**(`.v` + `.v2`) — `key === "lh"` 로 분기한다(D1·D8).
  자동 수집 출처는 **분양임대공고문 조회 서비스(15058530 `lhLeaseNoticeInfo1`)** 다.
  응답이 주는 것은 `PAN_NM`(공고명)·`AIS_TP_CD_NM`(세부유형)·`CNP_CD_NM`(지역명)·`PAN_SS`(공고상태)·`DTL_URL`(상세 URL) 이고,
  **보증금·월임대료·전용면적·접수기간·대상은 없다**(`DATA_SOURCES` §E — 접수기간은 요청 필터 전용 파라미터다).

  | 줄 | 내용 | 뜻 |
  |---|---|---|
  | `.v` | `감지 3시간 전 · 공고 3건` | 새 공고가 떴다는 사실 + 유형·지역·공고상태·상세URL 은 자동으로 안다 |
  | `.v2` | `상세 등록 2026-09-01` | 금액·면적·접수기간은 사람이 마지막으로 채운 날짜 |

  태그는 **`반자동`**. 한 줄로 뭉쳐 "자동"이라고만 적으면 사용자가 **금액까지 최신인 줄 오인한다.**
  원칙 3이 막으려는 바로 그 사고다. `.why` 는 `collectors[].note` 를 그대로 찍으며,
  거기에 "제목·유형·지역·공고상태·상세URL 은 자동, 금액·면적·접수기간은 수동"이 들어간다.
- "N시간 전"은 스케줄이 아니라 `meta.generated_at` 실측값으로 계산한다(cron 지연 때문).
- 🔴 **줄 순서는 SPEC §2 표 순서(`myhome → lh → bmc → trades → policy → private`)로 고정한다** —
  `meta.collectors[]` 배열 순서로 찍지 않는다(화면의 `FRESH_ORDER`). 배열 순서는 수집 실행 순서라
  성공·실패·재시도에 따라 실행마다 달라지고, 그러면 매일 같은 화면을 여는 사람 눈에 출처 줄이
  이유 없이 자리를 바꾼다. 목록에 없는 `key`(출처 추가분)는 **지우지 않고** 뒤에 배열 순서대로 붙인다.
- 🔴 **시각 표시는 `fmtDT()` 하나만 지난다.** 데이터는 ISO-8601(`…T14:59:25+09:00`)이고 화면은
  `2026-09-03 14:59` 다. 날짜만인 값(`detail_registered_at`·`verified_at`·`diff.date`)에는 없는 시각을
  `00:00` 으로 지어 붙이지 않고, 읽을 수 없는 값은 원문 그대로 남긴다(throw 금지 — M18 과 같은 태도).
  적용 지점: 상단바 수집 시각 · 신선도 바(`직전 성공`·`상세 등록`) · 공고 수집 실패 배너 ·
  정책 카드 `최종 확인` · 탭5 기준선 2곳 · 인쇄 헤더. **데이터 스키마는 ISO-8601 그대로 둔다.**

### 2-2. 판정 뱃지 · 신뢰도 뱃지

**판정 `.verdict` — 3단 + 사유 (사유 없는 뱃지 금지)**

```
[해당]  · 예비신혼부부 대상 · 통합공공임대 소득·자산 기준 충족     ← --low
[조건부] · 총자산·자동차 가액 미입력                                ← --mid
[불가]  · 부부 합산 소득이 기준 초과 (6,000만원 > 5,500만원)       ← --hi
```

**신뢰도 `.conf` — 정책 카드 전용 3단**

| 값 | 뱃지 | 색 | 판정에 미치는 영향 |
|---|---|---|---|
| `official` | 공식 출처 | `--bg-3` / `--fg-2` | 정상 3단 판정 |
| `secondary` | 2차 자료 | `--mid` | **불가 금지** → `조건부 — 수치 미검증` |
| `unverified` | 미검증 | `--hi` | **불가 금지** → `조건부 — 수치 미검증` |

🔴 **`official` 이 아닌 정책은 어떤 값이 들어와도 불가를 띄우지 않는다.**
강등할 때 원래 판정을 버리지 않고 뒤에 붙인다:

```
조건부 — 수치 미검증(2차 자료 기준). 공고문 확인 필요 —
        참고: 부부 합산 소득이 기준 초과 (6,000만원 > 5,000만원)
```

검증되지 않은 숫자로 사용자가 신청을 포기하면 실손해가 난다.
카드 안에도 같은 취지를 한 줄 적어, 왜 불가가 안 뜨는지 화면에서 읽히게 한다.

**불가를 막는 장치가 하나 더 있다 — 근사값** (SPEC §3-2)

소득 기준액을 공표표에서 직접 못 읽고 `100% × 비율` 로 폴백했다면,
**그 기준액에 걸린 탈락은 불가로 내지 않는다.** 문구는 SPEC 원문 그대로 쓴다.

```
조건부 — 기준액 근사값(공표표에 해당 비율 없음). 공고문·기관 확인 필요 —
        참고: 월평균 소득 5,000,000원이 기준 4,320,000원 초과 (2인 · 90% · 근사값)
```

🔴 **"해당"은 근사값이어도 그대로 허용한다. 이 비대칭은 의도된 것이다.**
잘못된 "해당"은 사용자가 공고문을 열어보는 과정에서 바로잡히지만,
잘못된 "불가"는 신청 포기로 끝나 되돌릴 수 없다. `confidence` 게이트와 같은 이유다.

### 2-2-1. "불가 → 조건부" 강등 게이트 **3종** (D3 · D11)

게이트는 **강등만** 한다. 판정을 바꾸되 **원인 문구는 지우지 않고 `참고:` 뒤에 남긴다** —
사용자가 무엇 때문에 걸릴 수 있는지 알아야 공고문을 열어 확인한다.

| # | 게이트 | 조건 | 강등 후 사유 | 배지 |
|---|---|---|---|---|
| 1 | **비official** | `confidence != "official"` | `조건부 — 수치 미검증(2차 자료 기준). 공고문 확인 필요 — 참고: …` | `.conf-secondary` / `.conf-unverified` |
| 2 | **근사값** | 기준액이 `100% × 적용비율` 폴백 | `조건부 — 기준액 근사값(공표표에 해당 비율 없음). 공고문·기관 확인 필요 — 참고: …` | `근사값 강등` (`.tag-mid`) + 적용액 옆 `근사값` 칩 |
| 3 | **완화 예정** | `pending_change` 있음 **이고** 불가 사유가 **소득 기준 초과** | `조건부 — 기준 완화 예정(확정 시 갱신) — 참고: …` | `완화 예정` (`.tag-mid`) |

- 🔴 **게이트 3종은 탭3 상단에 표로 항상 노출한다.** 왜 불가가 뜨지 않는지가 화면에서 읽혀야 한다.
  표 우측에 "지금 해당 N건"을 함께 세어 게이트가 죽어 있지 않음을 보인다.
- 🔴 **혼인 기간 초과는 게이트에 걸리지 않는다**(D5). 근거가 추정이 아니라 official 정책의 공고 원문이기 때문이다.
  이것이 v1.2 에서 **불가 범위를 넓히는 유일한 변경**이다.
- 게이트 2(근사값) 강등은 **기준 단위**다(D11). 정책 전체를 한꺼번에 강등하지 않는다 —
  그러면 유주택 같은 하드 불가 사유가 근사값 소득 사유에 삼켜져 사유 텍스트에서 사라진다.
- `pending_change` 는 **현행 수치를 바꾸지 않는다.** 카드에 `완화 예정` 배지 + `summary` 한 줄 + `source_url` 링크를 노출하고,
  `effective` 가 `"unknown"` 이면 "시행 시점 미확정"을 함께 적는다.

### 2-2-2. 정책 판정 결합 4단 (D11)

```
① 모든 기준을 개별 평가 (income / total_asset / net_asset / car_value /
   savings_months / savings_count / no_home / 혼인 / age_max / region)
   → 각 결과를 충족 · 조건부 · 불가 로 기록하고 "근사값 여부"를 함께 붙인다
② official 이고 근사값이 아니며 게이트에 걸리지 않는 불가 사유가 하나라도 있으면 → 불가
   사유는 해당하는 불가 기준을 전부 나열한다 (첫 사유에서 멈추지 않는다)
③ 그 외 조건부 사유(값 미입력 · 게이트 강등 · 추가 확인)가 하나라도 있으면 → 조건부, 사유 전부 나열
④ 전 기준 충족이면 → 해당
```

실측 사유 예 — 유주택 + 자산 3종 초과가 **한 줄에 모두** 남는다:
`불가 — 월평균 소득 …이 기준 … 초과 (2인 · 80%(70%+10%p 가산)) / 총자산이 기준 초과 (9억원 > 3억 4,500만원) / 자동차 가액이 기준 초과 (…) / 유주택 — 무주택 요건 미충족`

🔴 **②(불가)에서도 게이트 강등 원인을 `참고:` 로 남긴다**(검수 결함 #5). D11 은 "게이트는 강등만,
원인은 지우지 않고 `참고:` 뒤에"라고 정했는데, 하드 사유로 불가가 확정되는 경로에서 `notes` 를
버리면 **`근사값 강등`·`완화 예정` 배지가 사유 없이 남는다**(`.verdict` 3단은 항상 사유와 함께 — §2-2).

```
불가 — 총자산이 기준 초과 (99억 9,999만원 > 3억 4,500만원) / 자동차 가액이 기준 초과 (…)
     / 참고: 월평균 소득 5,833,333원이 기준 5,338,708원 초과 (1인 · 140%(120%+20%p 가산) · 근사값)
             — 기준액이 근사값이라 불가로 판정하지 않음                    [근사값 강등]
```

강등된 기준은 **불가 사유가 아니다.** 그래서 `참고:` 뒤로 밀고, 그 뒤에 "…라 불가로 판정하지 않음"을
붙여 읽는 사람이 배지와 문구를 연결할 수 있게 한다. 배지는 그대로 남긴다 —
배지를 떼는 쪽이 아니라 **원인을 남기는 쪽**이 원칙 4(잘못된 불가 금지)와 결이 맞다.
불변식: **배지가 붙은 판정에 `참고:` 가 없으면 결함**이다(등급 `no`·`cond` 양쪽).

### 2-3. D-day 뱃지 `.dday` — 임계 **7일 / 30일**

| 남은 일수 | 색 | 표기 |
|---|---|---|
| 7일 이내 | `--hi` | `D-5` |
| 30일 이내 | `--mid` | `D-21` |
| 그 외 | `--fg-2` / `--bg-3` | `D-45` |
| 당일 | `--hi` | `오늘 마감` |
| 접수 시작 전 | 위 색 유지 | `접수 전 · D-9` |
| 마감 지남 | `--fg-3` | `마감 (8/26)` |
| `apply_end` 없음 | `--fg-3` | `접수기간 미표기` + **`공고상태 {notice_status}` 칩**(D1) |

- 🔴 **`apply_end == null` 이면 D-day 를 계산하지 않는다**(D12 · M24). `d` 를 `null` 로 두고
  `null <= 7` 이 `true` 가 되는 경로를 만들지 않는다 — v1.1 은 `dd.d == null` 가드가 없어
  접수기간 미표기 공고가 `--hi` 로 새어 나왔다. 정렬에서는 `null` 을 맨 뒤(`9999`)로 보낸다.
- 접수 전이어도 **마감까지의 D-day 를 버리지 않는다.**
  목록 정렬이 마감 임박순이라 배지에서 사라지면 순서를 읽을 수 없다.
  시작·마감 날짜는 바로 옆 `접수기간` 칸에 이미 있으므로 배지에 다시 적지 않는다.
- 마감 지난 공고는 삭제하지 않고 접는다(새 소식에서 참조).

```
┌─────────────────────────────────────────────────────────────────┐
│ 통합공공임대 · 금정구 부곡동        [해당] 예비신혼부부 대상 …  │
│ 통합공공임대 부산금정 부곡지구 신혼부부 공급                    │
│ [일부 평형 가능]                          ← .fitchip            │
│ ─────────────────────────────────────────────────────────────── │
│ 임대보증금 1억 5,000 ~ 2억 4,000만원   월임대료 8 ~ 17만원      │
│ 전용 46.9 ~ 74.1㎡                     기준역까지 [기준역]      │
│ 접수 09/20 ~ 10/03 [D-30]              대상 신혼부부·예비신혼부부│
│ ─────────────────────────────────────────────────────────────── │
│ 공고 명시 배제 조건 — 유주택 세대 제외   ← .exclrow (있을 때만) │
│ 마이홈포털 · 자동 수집 · 수집 09-03 07:02  [공고번호 키]  원문 ↗ │
└─────────────────────────────────────────────────────────────────┘
```

🔴 **`null` 이 정상 케이스다**(SPEC v1.1 #1). 빈 값을 오류로 취급하지 않는다.

| 필드 | null 일 때 |
|---|---|
| `deposit_*` · `rent_*` | `공고문 확인 필요` 칩(`.chip-mask`) + **예산 판정 없음** |
| `area_*` | `미표기`(`--fg-3`) |
| `supply_type` | `유형 미표기` |
| `apply_start`/`end` | `접수기간 미표기` |
| `station_ids` 빈 배열 + `sigungu_code` 있음 | `역 매핑 없음` 칩 |
| `station_ids` 빈 배열 + `sigungu_code` 도 `null` | `지역 미표기` 칩. **지역 필터로 떨어뜨리지 않는다**(아래) |
| `target_groups` 빈 배열 | `미표기` + 판정은 **조건부**(불가 아님) |

**`detail_level` — 카드가 얼마나 채워졌는지** (SPEC 723줄 델타)

| 값 | 배지 | 뜻 |
|---|---|---|
| `detailed` | 없음 | 금액·면적·접수기간이 (있는 만큼) 채워진 공고 |
| `meta_only` | **`상세 미수집`** (`.fit-meta`, 점선) | 제목·등록일·링크만. LH 자동수집분의 기본값 |

`meta_only` 카드에는 배지 아래 한 줄로 이유를 적는다:
*"출처 API 가 제목·등록일·링크만 제공합니다. 금액·면적·접수기간·대상은 원문을 열어 확인하고,
필요하면 수동 등록으로 상세를 채웁니다."*

- `meta_only` 는 금액이 `null` 이므로 자동으로 **금액 미표기 묶음**에 들어간다. 예산 밖이 아니다.
- 사람이 `notices_manual.json` 에 상세를 채우면 `detailed` 로 승격되어 예산 판정 대상이 된다.
- 🔴 **지역 정보가 아예 없는 공고(`station_ids` 빈 배열 + `sigungu_code` null)는 지역 필터로 떨어뜨리지 않는다.**
  정보 부재를 탈락으로 처리하면 §3-2 가 경계하는 바로 그 사고가 난다.

**예산 2단 칩 `.fitchip` — 보증금·월임대료 두 축을 항상 적용한다** (SPEC §3-1 · D9·D10)

🔴 **사용자의 거래유형 선택(전세/월세)과 무관하게 두 축을 모두 판정한다.**
공공임대 공고는 대부분 보증금 + 월임대료가 함께 붙는다. 거래유형을 게이트로 걸면
기본 상태(전세만 선택)에서 **월세 축이 통째로 꺼져** 월임대료가 상한을 넘는 공고가 "전 평형 가능"으로 나온다.
같은 이유로 탭1의 `월세 상한` 필드를 거래유형으로 `disabled` 하지 않는다.

*보증금 축* — `가용액 = 보증금 가용액 + 대출 가능액`

| 조건 | 등급 | 사유 문구 |
|---|---|---|
| `deposit_min == null` | **판정 없음** | `임대보증금 하한 미표기` → `금액 미표기` 섹션. **상한이 있어도 판정하지 않는다**(D10) |
| `deposit_min` 있음 · `deposit_max == null` | `일부 평형 가능` | `보증금 하한 … 은 예산 내 · 상한 미표기` — 상한을 모르니 "전 평형"이라 말할 수 없다 |
| `deposit_max <= 가용액` | `전 평형 가능` | `보증금 전 평형(하한 ~ 상한)` |
| `deposit_min <= 가용액 < deposit_max` | `일부 평형 가능` | `보증금 … ~ … 중 일부만 예산 내` |
| `deposit_min > 가용액` | `예산 밖` | `보증금 최저 …이 가용액 초과` |

*월임대료 축* — `월세 상한` = 탭1 입력

| 조건 | 등급 | 사유 문구 |
|---|---|---|
| 월세 상한 **미입력** | **판정 없음** | `월임대료 상한 미입력` (보증금 축 결과만 쓴다) |
| `rent_min`·`rent_max` 둘 다 `null` | **판정 없음** | `월임대료 미표기` |
| `rent_max <= 상한` | `전 평형 가능` | `월임대료 전 평형(… ~ …만원, 상한 …만원)` |
| `rent_min <= 상한 < rent_max` | `일부 평형 가능` | `월임대료 일부 평형(… ~ …만원, 상한 …만원)` |
| `rent_min > 상한` | `예산 밖` | `월임대료 최저 …만원이 상한 …만원 초과` |

*두 축의 결합* — 등급을 `전 평형 가능 > 일부 평형 가능 > 예산 밖` 으로 두고 **둘 중 낮은 등급**을 최종 판정으로 쓴다.
한쪽이 `판정 없음` 이면 나머지 축 등급을 그대로, **두 축 모두 `판정 없음` 이면 `금액 미표기`**.
**사유(`.metanote`)에는 두 축의 근거를 모두 적는다** — 어느 축에서 걸렸는지 모르면 예산을 어떻게 고쳐야 할지 알 수 없다.

### 2-5-1. 예산 내 비율 — `deposit_hist` 히스토그램 (D6)

🔴 **분위수(p25/p50/p75)로 CDF 를 근사하지 않는다.** v1.1 목업은 조각선형 보간 계수(1.6 / 0.02 / 0.98)를
코드에 박아 근사값을 만들었고, 그 값이 `내 예산 이내 61%` 라는 **확정값처럼** 화면에 남았다(검수 M8·P6).
v1.2 는 수집기가 실은 히스토그램만 쓴다. `ratioWithin()` 에 `deposit_p25`·`deposit_p75` 참조가 **0건**이어야 한다.

```
데이터: trades.aggregates[].deposit_hist = [ {lo, hi, count}, … ]
        만원 단위 · 버킷 폭 = config.deposit_hist_bucket(기본 500) · lo 오름차순
        마지막 버킷은 hi: null 로 개방

비율 = ( Σ count[hi <= 가용액] + 가용액이 걸친 버킷의 선형 비례분 ) / Σ count
걸친 버킷 b 의 비례분 = b.count × (가용액 − b.lo) / (b.hi − b.lo)
마지막 개방 버킷(hi = null)에 걸리면 비례분은 0 — 상한을 모르므로 올려 세지 않는다
```

| 상태 | 화면 |
|---|---|
| 분모 `>= sample_min` | `내 예산 이내 N%` + `.pbar` + **캡션 `500만원 버킷 기준`** |
| 분모 `< sample_min` 또는 `deposit_hist` 없음 | `비율 계산 불가 — 표본 부족 또는 히스토그램 없음` (숫자를 만들지 않는다) |
| 조건 미입력 | 계산 자체를 하지 않고 탭4 비율 열은 `—` + 열 머리 `조건 필요` 칩 |

- **캡션에 버킷 폭을 반드시 적는다.** 버킷 폭만큼의 해상도 한계가 있음을 드러내는 것이 이 캡션의 목적이다.
  값은 `config.deposit_hist_bucket` 에서 읽는다(화면에 상수로 박지 않는다).
- 캡션 노출 지점 3곳: 탭2 시세 근거 카드의 비율 줄 · 탭2 `.trade-caption` · 탭4 `예산 내 비율` 열 머리.
- 같은 히스토그램을 **탭2 시세 근거와 탭4 비율 열이 공유한다**(`ratioWithin()` 한 함수). 두 화면이 다른 방식으로 계산하면 안 된다.
- 탭4 하단 `적용 설정값` 블록에 **`보증금 버킷 폭 500만원`** 줄을 추가한다.

**거래유형 분류**(SPEC §3-3)는 수집기가 정한다. 화면은 분류 결과를 표시만 한다.
`전세` = 월세 0 / `반전세` = 월세 > 0 이고 보증금 ≥ 월세 × `banjeonse_ratio` / `월세` = 그 외.

### 2-10. 민간 매물 딥링크 `.deeplink`

```
┌ 민간 매물은 수집하지 않습니다 ───────────────────────────────┐
│ 아래는 구서역 · 전세 만 담은 검색 링크입니다.                │
│ 여기서부터는 직접 확인하세요.                                │
│ [네이버부동산 ↗] [직방 ↗] [다방 ↗]                           │
│ 보증금·월세·소득 등 예산은 링크에 전달되지 않습니다.         │
│ 모든 외부 링크에 noopener noreferrer + referrerpolicy 적용.  │
└──────────────────────────────────────────────────────────────┘
```

- 🔴 **URL 쿼리에 넣는 값은 역명 + 거래유형뿐이다.** 보증금·월세·소득·자산은 넣지 않는다.
  링크를 누르는 순간 URL 은 외부 사업자에게 그대로 전달된다.
- 🔴 **모든 외부 링크에 예외 없이** `target="_blank"` + `rel="noopener noreferrer"` + `referrerpolicy="no-referrer"`.
  대상 = 딥링크 3개 · 공고 원문 · 정책 근거 출처 · **`pending_change` 발표 출처** · 신선도 바의 원문 목록 · 새 소식의 출처 열기.
  Referer 로 Pages 주소가 새는 것을 막는다.
- 🔴 **외부 링크는 `extLink(url, label)` 한 함수만 만든다**(M26 · P23). 속성 3종을 손으로 반복하면 한 곳이 빠진다.
  이 함수는 **`safeUrl()`** 을 지나며, `safeUrl()` 은 **`https?://` 로 시작하는 URL만** 통과시킨다.

  | 입력 | 결과 |
  |---|---|
  | `https://…` / `http://…` | 링크 생성 |
  | `javascript:…` · `data:…` · 상대 경로 · 빈 값 | **링크를 만들지 않고** `링크 형식 오류 — 원문 URL 확인 필요` 칩 (원문은 `title` 에만) |

  `notices_manual.json`·`policies.json` 은 **사람이 손으로 채우는 파일**이다. 스킴 검증이 없으면
  카드 링크가 그대로 스크립트 실행 경로가 된다. 조용히 링크를 지우지 않고 **오류를 보이게** 하는 이유는,
  사라진 링크는 아무도 고치지 않기 때문이다.
- 캡션에 "예산은 전달되지 않습니다"를 **명시**한다. 안 적으면 사용자가 확인할 방법이 없다.
- 이 블록은 항상 목록 **하단**. 위로 올리면 "이 도구가 매물을 준다"는 오해를 만든다.

**상단 고정 섹션** — 지역 필터를 걸면 신규가 0건인 날이 많다. 그래도 매일 열 이유가 남아야 한다.

- `신규` = `notices[].first_seen` 이 7일 이내이고 마감 전인 공고 (`--add-*`)
- `마감 임박` = **오늘 기준으로 다시 센 D-30 이내 전체**(D12). D-7 이내는 `--hi`, 그 밖은 `--mid`
- 0건이어도 **블록을 숨기지 않는다.** `최근 7일 신규 공고 없음` 한 줄로 남긴다.
- **조건 미입력 상태에서도 표시한다.** 예산과 무관하게 유효한 정보다.
- 🔴 **이 두 블록은 지역 필터만 반영한다**(M28). 공급유형·자격("해당"만) 필터와 예산은 적용하지 않는다.
  의도된 동작이므로 블록 아래 `.noteline` 한 줄로 **무엇을 세는지 밝힌다** — 밝히지 않으면
  사이드 필터를 걸었는데 건수가 안 변하는 것이 버그로 보인다.
- 마감 임박 블록 캡션에 `오늘 기준으로 다시 센 전체 — 새 소식 탭은 "새로 들어온 것"만 셉니다` 를 적는다(D12).
  탭5 와 건수가 다른 것은 모순이 아니다.
- 사이드 facet(공급유형·역)의 건수는 **전체 공고 기준**이며 다른 필터를 반영하지 않는다.
  이 사실도 facet 아래 한 줄로 밝힌다(M28).

**공고 자격 판정 — `linked_policy_id` 승계** (SPEC §3-2, **정식 필드**)

`notices.json` 에는 소득·자산 기준 필드가 없다. 공고 API 가 주지 않기 때문이다.
그래서 `linked_policy_id` 로 정책 판정을 승계한다. 값은 사람이 `notices_manual.json` 에서 지정하거나
공급유형 → 정책 매핑표(`config.json`)로 자동 부여한다.

| 조건 | 공고 판정 | 사유 문구 |
|---|---|---|
| `exclusions` 에 걸림 | **불가** | `공고 명시 배제 조건: 유주택 세대 제외` |
| 연결 정책이 **해당** | **해당** | `자격 기준 충족 (연결 정책: 행복주택)` |
| 연결 정책이 **조건부** | **조건부** | `연결 정책 판정에 총자산 미입력 (행복주택)` |
| 연결 정책이 **불가** | 🔴 **조건부** | `연결 정책 자격 미충족 (행복주택: 소득 기준 초과). 공고 기준은 다를 수 있으니 공고문 확인` |
| `linked_policy_id` 없음 | **조건부** | `연결된 정책 없음. 자격 대조 정보 없음` / 대상 표기만 있으면 `연결된 정책 없음. 대상 표기는 있으나 기준 대조 불가` |
| `linked_policy_id` 가 **없는 정책 id** 를 가리킴 | **조건부** | 🔴 `연결 정책({id})을 찾을 수 없음 — 설정 오류` (D20). `null` 과 **문구를 구분한다** — 같은 문구면 매핑 오타가 정상으로 위장된다. 목업 샘플 `MYHOME:2026-1160` 의 `p_happy_hous`(한 글자 오타)가 이 경로다 |

🔴 **정책의 "불가"를 공고로 승계하지 않는다.**
공고마다 소득·자산 기준이 본 정책과 다를 수 있고(회차별 완화, 우선공급 별도 기준),
연결 자체가 사람이 붙인 **추정**이다. 추정 위에 얹은 탈락 판정은 근거가 두 겹으로 약하다.
공고에서 불가를 낼 수 있는 근거는 `exclusions` 하나뿐이다. 그건 공고 원문 자체가 근거다.

- **승계 시 어느 정책에서 온 판정인지를 사유에 반드시 적는다.** 정책명 없는 승계 사유는 추적이 안 된다.
- 연결 정책의 `confidence` 가 `official` 이 아니면 **공고 카드에도 신뢰도 배지를 함께 단다.**
- `target_groups` 는 **표시용**이다. 원문 대상 표기를 그대로 보여주되 판정 근거로는 `linked_policy_id` 를 우선한다.

| 묶음 | 표시 | 이유 |
|---|---|---|
| 1. 예산 내 | 카드 + `전 평형` / `일부 평형` 칩 | — |
| 2. 금액 미표기 | 카드. **접지 않는다** | 판정 불가지 탈락이 아니다 |
| 3. 예산 밖 | `예산 밖 N건 접힘` 한 줄. 카드를 그리지 않는다 | `DESIGN.md` §3 |

**지역 필터** `13역 인근`(기본) ↔ `부산 전역`. 상태는 `UI.region = "near" | "busan"` 하나뿐이다.

13역 결과가 0건이면 부산 전역 건수를 자동 안내하고 `부산 전역으로 보기` 버튼을 빈 상태 안에 둔다.
필터로 가려진 건수는 목록 아래 `.noteline` 으로 항상 알린다.

🔴 **판정은 `inRegion(n)` 한 함수에만 있고, 그 함수가 `UI.region` 을 읽어야 한다**(검수 결함 #1).
순서를 지킨다 — 뒤바꾸면 두 규칙 중 하나가 죽는다.

```
function inRegion(n){
  1) station_ids 빈 배열 + sigungu_code == null  → true   // §2-4 지역 미표기 보호. 무조건 먼저
  2) UI.region === "busan"                        → true   // "부산 전역" = 필터를 끄는 선택
  3) station_ids 중 하나가 활성 역 필터에 있으면  → true
}
```

- ②의 근거: **공고 수집 범위 자체가 부산 전역**이고 13역은 화면 필터일 뿐이다(탭2 `.banner.note`).
  그래서 `부산 전역` 에서는 역 매핑 유무를 보지 않는다. `sigungu_code` 로 부산 여부를 다시 검사하지 않는다 —
  수집 범위 밖 공고를 화면이 걸러 주는 척하면, 실제로 범위가 넓어진 날에 조용히 사라진다.
- ②가 없으면 `부산 전역으로 바꾸면 N건이 더 있습니다` 안내와 `[부산 전역]` 버튼이
  **보여줄 수 없는 것**을 가리킨다. 결함 #1 이 정확히 그 상태였다.
- 지역 필터를 **읽는 곳은 두 군데**다 — 목록 3묶음(`computeHomes()`)과 상단 고정 섹션(`fixedSection()`).
  둘 다 같은 `inRegion()` 을 지난다. 고정 섹션이 지역 필터만 반영하는 것은 M28 대로다.
- `13역 인근` ↔ `부산 전역` 전환은 `renderHomes()` **재렌더**로 끝난다. 라벨·힌트·`.noteline` 만
  바꾸고 목록을 그대로 두면 안 된다(결함 #1 의 증상).

🔴 **`note` 는 `.kv` 의 `비고` 가 아니라 접힘(`details.datanote`) 안에 "데이터 메모"로 둔다. 기본은 닫는다.**
`policies.json` 의 `note` 는 조사자·개발자용 메모다 — 필드명(`pct_dual = null`)·`**강조**`·1·2차 조사 이력이
그대로 들어 있고, v1.2 는 그걸 본문에 찍어 **정책 카드에서 가장 긴 줄이 사용자에게 뜻 없는 개발 메모**가 됐다.
지우는 것도 답이 아니다 — 판정 수치의 근거와 한계가 여기에만 적혀 있다(예: 럭키7하우스가 왜 2차 자료인지).
그래서 **화면·인쇄 모두 접힘 안**에 두고, `summary` 로 성격을 밝힌다("조사·정리용 기록이며 신청 조건이 아닙니다").
인쇄 직전 `<details>` 강제 펼침 대상에서 **`details.datanote` 는 제외한다** — 강제 펼침은 원래 예산 밖 공고를
위한 규칙이다(DESIGN.md §3). 빈 문자열·`null` 이면 접힘 자체를 만들지 않는다(빈 접힘은 클릭할 것이 없다).

⭐ **소득 줄에 3가지를 함께 찍는다** — 기준 비율 / 지금 내 가구원수·**가산 반영 비율**의 적용 금액 / `year_label`.
`기준 중위소득 100% 이하 · 2인 · 110%(100%+10%p 가산) 적용액 4,619,221원 [근사값] │2026년도 기준 중위소득(2026-01-01 적용)`
비율만 적으면 사용자가 자기 숫자와 비교할 수 없다. 기준액이 없으면 `기준액 미확보`,
가구원수 미입력이면 `가구원수 미입력 — 적용비율 계산 불가`(숫자를 만들지 않는다).

**`혼인` 줄** (D5) — `marriage_within_months` 를 년 단위로, `pre_marriage_*` 를 문구로 적는다.
`혼인 7년 이내 · 예비신혼 인정` / `예비신혼 불인정` / `예비신혼 인정 3개월 이내`.
v1.1 은 이 세 필드를 카드에 전혀 노출하지 않아 기혼 판정이 왜 그렇게 나오는지 화면에서 읽히지 않았다.

**`근사값` 칩**은 표에 그 비율 칸이 없어 `100% × 비율` 로 폴백했을 때만 붙인다(1-3).
칩에 `title` 로 "표에 이 비율 칸이 없어 100% 값에 비율을 곱했습니다"를 넣는다.

> ✅ **해소됨**: 앞선 검토에서 "근사값에 근거한 불가가 나올 수 있다"고 짚었던 문제는
> SPEC §3-2 가 **근사값 기반 불가 금지**를 규칙으로 확정하면서 해결되었다(2-2-1 게이트 2).
> v1.2 실샘플은 **통합공공임대**다 — 기준중위소득 표에 2인 `110%` 칸이 없어(고시가 100%만 공표)
> `100% × 110 ÷ 100` 폴백으로 가고, 그 기준에 걸린 탈락은 `조건부 — 기준액 근사값(…)` 으로 강등된다.
> 강등은 **기준 단위**이므로 같은 정책에 유주택 같은 하드 불가가 있으면 그쪽은 그대로 불가로 남는다(D11).

| `verified_at` 90일 초과 | `--mid` — 확인한 지 N일 지났습니다 |
| `confidence != official` | `--mid` — 이 정책은 어떤 값을 넣어도 불가로 판정하지 않습니다 |
| `pending_change` 있음 | `--mid` — **`완화 예정`** + `summary` 한 줄 + `effective` 상태 + **발표 출처 링크**(D3) |

- 🔴 **변경 감지는 해시 비교 하나로만 판단한다.** v1.1 목업은 `source_changed` 플래그와 해시 비교를
  둘 다 요구해 근거가 2중화됐다(검수 스키마 불일치 지적). SPEC §3-6 에 `source_changed` 필드는 없다.
- 🔴 **`verified_at` 은 `isNaN` 가드를 지난다**(M18). v1.1 은 `daysBetween` 결과를 그대로 찍어
  `최종 확인 (NaN일 전)` 이 나오고 **90일 경고가 무음**이 됐다. 읽을 수 없는 값을 화면에 그대로 옮기지도 않는다
  (`최종 확인일(null)` 같은 문구가 나오면 안 된다).
- `content_id` 는 `#id` 하나만 받는다(D14). `content_selector` 는 폐기된 필드명이다.

**상태**: 조건 미입력이어도 정책 카드를 감추지 않는다. 목록으로서의 가치가 있다.
상단에 `.banner.warn` 로 "조건을 입력하면 해당/불가로 갈립니다"만 붙인다.

- 섹션 5개는 **건수 0이어도 머리글을 남기고** 안쪽만 `변경 없음`.
  지우면 "오늘 확인했다"는 사실이 사라진다.
- 전부 0건이면 `직전 수집과 달라진 것이 없습니다` + 마지막 수집 시각.
- 마감 임박 임계는 **D-7 / D-30**.
- 이 섹션의 건수는 `diff.closing_soon`(이번 수집에서 **새로 임계 안으로 들어온** 공고)이고,
  탭2 고정 섹션은 **현재 D-30 이내인 전체**다. 두 숫자가 달라도 모순이 아니다.
  **그 사실을 이 섹션 위 `.noteline` 에 한 줄로 적는다**(D12).
- 🔴 **`closing_soon[].dday` 를 데이터 그대로 표시한다**(D12). 오늘 다시 계산하지 않는다 —
  이 섹션이 세는 것은 "그때 새로 들어온 것"이라 그때의 D-day 가 근거다.
  `dday` 가 `null`·비정상이면 `D-day 미산출` 로 적고 `--hi` 로 새게 하지 않는다(M24).
- `마감됨` 섹션은 `closed_notices[].reason`(`apply_end` / `notice_status` / `disappeared`)으로 **문구를 구분한다**(2-4 표).
- 🔴 **오늘치와 히스토리 항목을 같은 렌더 함수로 그린다**(`diffSections()`). 두 형태가 같기 때문이다(D21).
  히스토리를 `diff.history` 로 중첩하면 항목에서 `is_first_run`·`closing_soon` 이 누락되고, 그러면 히스토리 렌더가 오늘치와 갈린다.
  `보관 이력` 모드에서 히스토리 각 날짜를 `<details class="daybox">` 로 접어 **5섹션 전부** 그린다.
- 🔴 **`is_first_run` 이면 2-9 카드 하나만.** 이 화면은 **`DATA.diff.is_first_run` 데이터로만 도달한다**(M3·D21).
  목업 전용 버튼은 그 값을 **토글**할 뿐 별도 화면 경로를 만들지 않는다 — 별도 경로를 두면
  버튼을 제거하는 순간 SPEC §4 Q53(첫 실행) 항목이 무조건 실패한다.
- 실패 항목(`collector_failures[].key`)으로 수집기를 찾아 이름을 표시한다. 한국어 `name` 으로 대조하지 않는다(D8).
- 🔴 **⑤ 섹션도 `status` 3종을 구분해 그린다**(SPEC §3-6 `collector_failures[].status`). 화면 표 `FAILURE_STATUS`:

  | status | `.news-item` | 마크 | 항목 문구 |
  |---|---|---|---|
  | `fail` | `.is-fail` (`--hi`) | `✕` | `{수집기명} — 수집 실패` |
  | `skip` | `.is-off` (`--fg-3`) | `—` | `{수집기명} — 이번 실행 건너뜀` |
  | `hold` | `.is-warn` (`--mid`) | `⏸` | `{수집기명} — 0건 수집 — 마감 판정 보류` |

  `status` 가 없는(옛) 항목은 `fail` 로 본다. 세 경우 모두 `사유: {error} · 마지막 성공 {fmtDT}` 를 `.sub` 에 적는다.
  **섹션 머리글은 `⑤ 수집 실패` 로 고정**한다 — 건너뜀·보류도 "이번 회차에 못 채운 것"이라 같은 자리에서 세는 게 맞고,
  머리글을 바꾸면 SPEC §4 Q22 의 문구 대조가 흔들린다. 구분은 항목 문구·색이 한다.
  🔴 **skip 항목을 목록에서 지우지 않는다**(원칙 7 — 조용히 넘기지 않는다). 회색으로 낮춰 적는다.
- 비교 기준이 `notices_prev.json` 임을 화면에 적는다.
  Actions 러너는 매회 새 체크아웃이라 git 히스토리가 아니라 커밋된 이 파일이 기준이라는 사실이
  실제 구현을 가른다.
- 정책 변경은 **같은 해시를 두 번 알리지 않는다**(`last_notified_hash`).
  경보 피로가 쌓이면 진짜 변경을 놓친다.

### 7-5. `build.py` 개발자가 승계할 때의 함정

| # | 함정 | 이유 |
|---|---|---|
| 1 | `data-mock-only` 3곳을 지울 때 **`bindInputs()` 의 "목업 전용 블록" 주석 구간을 함께** 지운다 | 핸들러만 남으면 `$("btn-sample")` 이 `null` 이 된다. 지금은 null 가드가 있어 죽지 않지만, 죽은 코드를 남기면 다음 사람이 버튼을 되살리려 한다 |
| 2 | 목업의 `NOW = parseDT(DATA.meta.generated_at)` 를 **`new Date()` 로 바꾼다** | 목업은 샘플 날짜가 고정이라 `generated_at` 을 "지금"으로 삼는다. 실 빌드가 이걸 승계하면 D-day 가 수집 시각에 고정돼 하루가 지나도 갱신되지 않는다. 반대로 신선도 바의 "N시간 전"은 **`generated_at` 실측값**을 써야 한다(SPEC §2) — 두 용도를 구분해야 한다 |
